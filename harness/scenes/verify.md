# 自测与验收场景

## 验收方式判定

按实际行为和影响判定，不按修改行数、文件数量或执行者对代码的熟悉程度判定。先检查下表是否命中；**任一条件命中，就必须安排独立 QA**，不能只写“必要时”。

| 触发条件 | 典型范围 | 独立验收重点 |
| --- | --- | --- |
| 新增功能，或改变用户操作流程 / 业务规则 | 新增操作入口、修改提交条件或状态流转 | 从用户目标核对正常、边界和错误路径 |
| 涉及登录、权限或会话行为 | 路由保护、Token、登录 / 退出 | 授权边界、失效状态和恢复流程 |
| 涉及删除、数据保存或字段转换 | 关联删除、编辑保存、序列化、数据迁移 | 数据完整性、失败处理及保存回读 |
| 涉及前后端契约变化 | 字段、响应结构、分页、业务域或校验规则 | 前后端一致性及兼容范围 |
| 影响多个模块或公共能力 | 共享组件、公共状态、请求封装 | 受影响调用方和回归路径 |
| 修改交互或设备适配，需要运行页面才能判断结果 | 离页提醒、导航、手机适配 | 实际操作、触屏 / 键盘可达性和目标尺寸 |
| 同一问题反复出现，或验证结论存在争议 | 回归问题、修复后仍复现、结果与证据不一致 | 独立复现、遗漏前提及修复证据 |

所有任务仍需执行角色先自检，独立 QA 不替代开发自测。独立指由原实现者之外的角色验收，不得把原实现者再次自测记为独立 QA。按任务需要顺序安排，不因此自动开启多个并行代理。

未命中任何触发条件时，以下任务可由执行角色自检：

- 文档、注释和链接调整：核对事实、格式、引用与导航。
- 单一页面的简单文案或局部样式：不改变交互、响应式策略、公共样式或业务含义，并检查相关运行页面。

任务名称不决定验收方式。例如“文案调整”如果实际改变业务提示含义或操作规则，仍按上表判断。

缺少环境、账号、测试数据或可运行页面，不能作为“不需要 QA”的理由。命中条件后仍记为“需要独立 QA，当前受阻”，明确缺失条件、已完成检查与未覆盖范围；不得降级为自检通过或宣称验收完成。

## 执行与复验

1. 以用户要求和本次差异确定验收范围，读取 [验证规范](../test-spec.md) 中相关检查。
2. 按上述判定记录“执行角色自检”或“必须独立 QA”，注明命中的条件及影响范围；独立 QA 仅接收目标、范围、受影响文件和证据路径，避免复制完整上下文。
3. QA 记录实际结果和复现步骤，将普通问题直接交回原开发角色；开发修复后原 QA 只复验受影响范围。
4. 关键业务歧义、验收争议、范围变化或两轮自主修复失败才升级主 Agent / Sol。
5. 最终区分自动检查通过、人工验证通过、未验证及受阻项；技术检查通过不代替用户业务验收。

验收记录至少包含：改动 / 提交、验收方式及判定依据、执行角色、环境、检查项与结果、证据路径、未验证或受阻项。

## 本项目适用示例

- Harness 文档和链接维护：执行角色自检。
- 标签隔离、删除保护、重名规则、空块校验、碎片分页：命中业务规则、数据或接口条件，必须独立功能 QA。
- 未保存离页提醒：必须独立验证返回、切页、刷新 / 关闭、取消离开及保存成功 / 失败路径。
- 手机适配：必须独立检查已确认的登录、查看、编辑并保存流程，不把新建、删除或分类 / 标签管理扩大为手机必需范围。

发布后的检查参照 [README 发布指南](../../README.md#-部署指南)。涉及真实业务数据的写入与删除须在任务授权范围内进行。
